## 実行手順（この順で必ず実施）

### 0. 準備

- 作業ディレクトリはリポジトリルート。
- `TZ=Asia/Tokyo date "+%Y-%m-%d"` で本日の日付を確認する。
- `.venv` が無いか API 用パッケージが無い場合は、`SETUP.md` に沿い依存を入れ、認証疎通を確認する。
- 秘密情報（JSON鍵・トークン全文）をチャットやレポートに出力しない。

### 1. データ収集（実測）

次を実行する（引数はユーザー指定があればそれを使う）。

```bash
source .venv/bin/activate
python scripts/collect_analysis_data.py
```

成功したら `reports/<run_id>/raw/` の CSV と `summary.json` を読む。  
失敗したら原因（認証 / API未有効 / 権限 / 設定ミス）を切り分け、レポートの「計測上の問題」に記録する。無理に数値を埋めない。

集計の約束:

- 基本期間は分析日から約1か月（スクリプト既定28日）。前期比は同日数の直前期間。
- `site=blog` は `page` が `/blog` または `/blog/` 始まり。それ以外は `lp`。
- `form_click_ga4.csv` と `prev_form_click_ga4.csv` の `googleform_click` は参加フォームへのリンククリック。フォーム送信完了と混同しない。
- フォーム送信完了数が別途取得できない場合は「未計測」と明記し、リンククリック数から推測しない。

### 2. コンテンツ実査（LP / ブログ）

次を確認し、`reports/<run_id>/content-notes.md` にメモする。

- LP: https://hagakurepgm.net
- ブログ: https://hagakurepgm.net/blog/

確認項目（`plan.md` 準拠）:

- ページタイトル、見出し、メタディスクリプション
- CTA / 参加申し込み導線（Googleフォーム等）
- 内部リンク・外部リンクの主なもの
- LP↔ブログの行き来しやすさ
- モバイルで読めそうか（可能な範囲）

取得できない項目は「未確認」と書く。

### 3. 分析（`plan.md` Step 2）

実測と実査だけを根拠に、少なくとも次を扱う。

**LP**

- 趣旨・活動が伝わるか / 参加検討に足りる情報か
- 検索・外部からの獲得 / 参加フォームリンクのクリック / 関連ページへの移動
- 紹介ツールとしての使いやすさ / 運営継続しやすさ

**ブログ**

- 活動・学習事例の入口か / 検索流入
- 読まれているテーマ / LP・参加案内への移動
- アウトプットの場としての利用（投稿数・更新。分かる範囲）
- 運営が学習機会になっているか（プロセス面。分かる範囲）

原因は次の表で整理する（事実と仮説を混ぜない）。

| 確認された事実 | 原因の仮説 | 仮説の根拠 | 追加で必要なデータ | 検証方法 |
| --- | --- | --- | --- | --- |

### 4. 改善アクション（`plan.md` Step 3・6）

アクションを A / B / C に分類する。

- A: すぐできて短期反応が期待できる
- B: すぐできて長期反応が期待できる
- C: 時間がかかるが長期反応が期待できる

各アクションに、対象サイト・対象者・課題・根拠・実施内容・期待効果・優先度・効果指標・確認時期を付ける。

優先順位では、アクセス増だけを上位にしない。次を必ず考慮する。

- 学ぶ楽しさ、気軽な参加・共有、教え合い、地域の緩やかなつながり
- 参加者に過度な負担をかけない
- サイト開発・運営自体が学習機会になる

売上・急拡大前提の施策は提案しない。

### 5. KGI / KPI

`plan.md` §4 の空きを埋め、提案として書く（現状値が不明なら「現状: 未計測/要確認」）。

アクセス数そのものを KGI にしない。対象者ごとに「目的が達成できているか」が分かる指標にする。

### 6. 成果物の保存

次を必ず書く。

1. `reports/<run_id>/report.md` … 本体（構成は下節）
2. `reports/<run_id>/content-notes.md` … 実査メモ
3. `reports/<run_id>/raw/` … 収集スクリプト出力（既存）

チャットには、エグゼクティブサマリーと、保存したファイルパスを短く返す。

## 分析原則（違反禁止）

- 実測・計算・推測・仮説を区別する。不足なら断定しない。
- 指標の増減だけで良し悪しを判断しない。
- コミュニティ目的と無関係な指標を過度に重視しない。
- 一般的なWebマーケ成功基準をそのまま当てない。
- 提案は取得データと確認コンテンツを根拠にする。
