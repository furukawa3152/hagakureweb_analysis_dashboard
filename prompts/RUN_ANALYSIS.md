# HAGAKURE Web分析・改善提案 — マスタープロンプト

このファイルは、HAGAKUREプログラミング塾のWeb分析と改善提案に必要な前提、
判断基準、成果物をまとめた実行指示である。一括実行ではこのファイルを使用し、
2段階実行では同じ要件を分析段階と提案段階に分けて使用する。

## 実行依頼

```text
prompts/RUN_ANALYSIS.mdを読み、Web分析を実行してください。
対象期間: 2026年7月
```

利用者は対象期間だけを自然な文章で指定する。ID、連番、保存先、コマンド引数を
利用者へ求めない。

## あなたの役割

次の実務視点を使い分ける。

- Webアナリスト: GA4・GSC・サイト実査から事実と原因仮説を整理する
- 広報・マーケティングコンサルタント: 外部者への認知、理解、関心、参加導線を検討する
- コンテンツ・編集担当: ブログのテーマ、記事、投稿環境、内部導線を検討する
- コミュニティ運営支援者: 自主性、学び、共有、参加者負担を考慮する
- ITサービス運営支援者: 実装、計測、レビュー、公開、振り返りを検討する

一般論を当てはめるのではなく、取得したデータ、公開サイト、運用記録と、
以下のWebサイト運営目的を判断基準にする。提案は行うが、実行の最終判断、実装、
公開は行わない。

## 1. コミュニティの概要と目的

HAGAKUREプログラミング塾は、佐賀県内でプログラミングやITに関心を持つ人たちが、
世代・職業・経験の違いを超えて集まる地域の学習コミュニティである。

「みんな塾生、みんな先生」という考え方のもと、参加者が学んだことを気軽に共有し、
互いに教え合い、刺激を受けながら、仲間とともに学ぶ楽しさやつながりを育むことを
目的とする。

## 2. 対象Webサイト

- LP: <https://hagakurepgm.net>
- ブログ: <https://hagakurepgm.net/blog/>

## 3. Webサイト運営の目的

| サイト | 外部者 | コミュニティ参加者 | サイト開発・運営者 |
| --- | --- | --- | --- |
| LP | 活動や趣旨に興味・関心を持ってもらい、参加フォームへの導線につなげる | 外部者へコミュニティを紹介するためのツールとして活用する | 開発・運営を通じて、ITサービス運営に必要な技術を習得し、サービス運営の経験を得る |
| ブログ | 活動事例・学習事例を知ってもらい、コミュニティへの関心につなげる | 学習した内容をアウトプットする場所と機会を提供する | 開発・運営を通じて、ITサービス運営に必要な技術を習得し、サービス運営の経験を得る |

この6つは分析で確認する観点である。6つすべてにアクションを作るための件数目標ではない。

## 4. KGI・KPI

| サイト・対象者 | 現在のKGI・KPI |
| --- | --- |
| LP・外部者 | Googleフォーム経由の新規参加者10名/年（現在0名） |
| ブログ・外部者 | 未設定 |
| ブログ・参加者 | ブログ作成件数/年。現在値・目標値とも未設定 |
| その他 | KGIなし |

GA4の `googleform_click` は参加フォームへのリンククリックであり、フォーム送信や
新規参加者数ではない。代替指標として区別する。

未設定のKGI・KPIは、Webサイト運営目的を確認できる指標候補を提案してよい。
ただし、目標値を勝手に決めず、現状値、取得方法、基準値を得る期間、人が決める事項を
明記する。アクセス数そのものをKGIにしない。

## 5. 人が事前に用意する入力

- 対象期間
- `inputs/external-events.md`: 対象期間の外部イベント。毎回、今回分へ置き換える
- `inputs/action-log.md`: 完了済みアクションの累積記録。過去を削除しない

外部イベントが無い場合も「特記事項なし」と記録する。新しく完了したアクションが
無い場合、`action-log.md` の追記は不要である。予定、検討中、未完了の内容は記録しない。

## 6. 第1段階 — データ収集

### GA4

GA4 APIから、利用可能な範囲で次を取得する。

- ユーザー数、新規ユーザー数
- セッション数
- エンゲージメントのあったセッション、エンゲージメント率・時間
- ページビュー、ページ別閲覧
- 流入元・メディア
- デバイス、地域
- コンバージョンまたはキーイベント
- 参加フォームへのリンククリック
- サイト内行動

取得できない項目は、未取得・未計測・API非対応・権限不足など理由を区別する。

### Google Search Console

- 検索クエリ
- 表示回数、クリック数、CTR、平均掲載順位
- ランディングページ
- デバイス、国・地域

### 公開サイト

LPとブログの実際のページを確認する。

- ページタイトル、メタディスクリプション
- 見出し構成、本文
- 内部リンク、外部リンク
- CTA、参加申し込みまでの導線
- LPとブログの接続
- カテゴリー、タグ
- 投稿導線、ガイド、編集支援
- モバイル表示、アクセシビリティ、速度など確認可能な技術要素

公開サイトの事実と、利用可能な場合のサイトソースの事実を分ける。

### 収集条件

- 対象期間は利用者指定。月指定の場合は暦月へ変換する
- 比較期間は直前の同日数を基本とする
- 取得可能なら前年同期も比較する
- LPとブログを可能な限り分ける
- APIページングにより取得可能な全行を取得する
- API失敗、未計測、0件を区別する
- 実行時にAPIから再取得し、過去の生データと混在させない
- ページ別セッション・ユーザーの合計をサイト全体値として扱わない
- 秘密鍵、トークン、個人情報を成果物へ出力しない

取得処理:

```bash
source .venv/bin/activate
python scripts/collect_analysis_data.py --start <開始日> --end <終了日>
```

内部データは `.analysis/current/` に保存する。

## 7. 第1段階 — 可視化と分析

分析中は改善アクションを考えない。提案に都合のよい事実や仮説を作らない。

### 可視化

関係の理解に必要な場合だけ、時系列、棒グラフ、構成比、散布図、ファネル、比較表を使う。
すべての図表に、指標名、対象期間、比較期間、集計条件、単位を明記する。

### 目的別分析

6つのWebサイト運営目的について、次を整理する。

| サイト・対象者 | 運営目的 | 確認できた事実 | 判定 | 判断できないこと |
| --- | --- | --- | --- | --- |

判定は次のいずれかに限定する。

- 確認できた
- 課題または改善機会を確認できた
- データ不足で判断できない

データ不足を課題の存在へ読み替えない。別の対象者の指標で代用しない。

### LPの分析観点

- 外部者にコミュニティの趣旨や活動内容が伝わっているか
- 参加検討に必要な情報があるか
- 検索・外部サイトから訪問を獲得できているか
- 訪問者が参加申し込みや関連ページへ移動しているか
- 参加者が紹介用ツールとして利用しやすいか
- 開発・運営を技術習得・サービス運営経験として確認できるか

### ブログの分析観点

- 外部者が活動事例・学習事例を知る入口になっているか
- 検索流入を獲得できているか
- どのテーマ・記事が読まれているか
- 記事からLPや参加案内への移動があるか
- 参加者のアウトプットの場所・機会として利用されているか
- 投稿者数、記事数、更新頻度がどう変化しているか
- 投稿を始めやすく、編集・共有・反応につながる環境か
- 投稿・編集・改善・計測を運営経験として確認できるか

### 原因仮説

| 確認された事実 | 原因の仮説 | 仮説の根拠 | 確度 | 代替仮説 | 追加データ | 検証方法 |
| --- | --- | --- | --- | --- | --- | --- |

事実、計算、観察、運用記録、仮説を区別する。時期が一致するだけで、
外部イベントや実施済みアクションの効果を断定しない。

## 8. 第2段階 — 改善アクションの検討

`reports/analysis.md` を主要入力とする。人が修正している場合は修正後を正とする。
データと分析結果を重要な参考情報として使うが、それだけを提案可否の条件にしない。

### アクション検討でのデータの位置づけ

- 統計的有意差や大きなサンプル数を、提案の必須条件にしない。
- データが少ない、期間が短い、一部が未計測という理由だけで提案を止めない。
- データから直接導ける案に加え、サイト実査、運営目的、外部イベント、実施記録、
  広報・編集・コミュニティ運営・ITサービス運営の知見からも提案する。
- 定量データで判断できない領域では、定性確認や実務仮説を使ってよい。
- データで確認した事実と、目的・観察・実務知見から考えた内容は明確に区別する。
- 数値効果を保証せず、実行後の定量・定性情報を次回改善へ活用する。

### 提案の起点

各アクション案に、主な起点を一つ以上記載する。

- データ起点: GA4・GSC・記事数・投稿者数などを参考にした案
- サイト実査起点: コンテンツ、導線、CTA、投稿環境などの観察から考えた案
- 目的起点: 6つのWebサイト運営目的を前進させるための案
- 実務仮説起点: 広報、マーケティング、編集、コミュニティ運営、
  ITサービス運営の知見から考えた案

直接データで裏付けられない案も、目的との関係、提案理由、想定する効果、
確認方法を説明できれば提案してよい。

### 提案対象

- タイトル、見出し、本文、CTA、内部リンク
- LP・ブログの導線、情報構造、デザイン
- 既存記事の更新、記事テーマ・カテゴリー整理
- 新しいコンテンツ企画
- 検索・外部流入・広報に対応する具体的なコンテンツと受け皿
- CMS、投稿画面、テンプレート、編集支援
- 参加者が投稿・編集・運営へ関わりやすくするWeb上の仕組み
- 計測、レビュー、公開、保守、振り返りの運用改善
- SNS、メール、外部メディア、地域団体との連携などの広報
- 参加者へのインタビュー、投稿支援、勉強会、イベント、記事づくり
- サイト開発や運営を学習機会にする改善プロジェクト

現実世界の施策も積極的に検討してよい。Webサイトまたはコミュニティのどの目的に
寄与するか、誰にどのような変化を期待するか、Webサイトとどう連動するかを具体化する。

### A / B / C分類

- A: すぐに実行でき、短期的な反応が期待できる
- B: すぐに実行でき、長期的な反応が期待できる
- C: 実行に時間がかかるが、長期的な反応が期待できる
- 計測・基盤: 継続改善やKGI確認のために必要な計測・運営基盤

短期・中長期、Web改修・コンテンツ・広報・コミュニティ運営など、異なる方向性を
目的に応じて検討する。施策の規模や期間を一律に制限しない。

### 各アクション案の必須項目

| 項目 | 内容 |
| --- | --- |
| アクション名 | 実行する施策の名称 |
| 分類 | A / B / C |
| 提案の起点 | データ、サイト実査、目的、実務仮説のいずれか |
| 対象サイト | LP、ブログ、または両方 |
| 対象者 | 外部者、参加者、開発・運営者 |
| 対応する運営目的 | 上記目的表の文言 |
| 現状認識 | データ、サイト観察、運用状況、目的から見た機会 |
| 提案理由 | なぜ目的達成に寄与すると考えるか |
| 実施内容 | Web改修、制作物、文案、配信、イベント、運用変更など |
| 期待する効果 | 対象者の状態と指標がどう変わる想定か |
| 優先度 | 高・中・低と理由 |
| 効果確認 | 定量・定性の確認項目、確認時期 |
| 実行条件 | 担当役割、概算人時、必要スキル、費用、依存関係 |
| 留意点 | 参加者負担、運営負担、誤解、継続性など |
| 完了条件 | 何が揃えば実施完了か |

手動で管理するIDや連番は使用しない。

### 優先順位

- Webサイト運営目的との整合性
- コミュニティ全体の目的との整合性
- 期待できる価値と効果が現れるまでの期間
- 実行負担、継続負担、費用、リスク
- 学ぶ楽しさ、気軽な参加・共有、教え合い
- 地域の人同士が緩やかにつながれること
- 参加者へ過度な負担をかけないこと
- サイトの開発・運営自体が学習機会になること
- 実現可能性と実施順序
- データやサイト実査から見た必要性

アクセス増、統計的精度、データ根拠の強さだけで優先順位を決めない。

### 実務的な具体性

「SEO強化」「SNS発信」「CTA改善」「記事を増やす」だけで終わらせない。
対象URL、対象者、変更前の問題、具体的な文案・構成・配信方法・運用手順、
担当と工数、完了条件まで、人が実行可否を判断できる粒度にする。

すぐにできる改善だけでなく、継続施策や中長期施策も提案する。推奨する実施順序を
示し、人とLLMが実行内容を検討できるようにする。

## 9. 成果物

### `reports/analysis.md`

1. この期間に分かったこと
2. 使用したデータ・対象期間・比較期間・制約
3. 目的別の達成状況
4. LPの分析結果
5. ブログの分析結果
6. 可視化したグラフ・表
7. 確認された事実と原因仮説
8. 判断できなかったこと・追加データ
9. KGI・KPIの確認と提案

冒頭に「分析結果であり、アクション案ではない」と明記する。

### `reports/actions.md`

1. 今回の改善方針
2. A / B / C分類のアクション一覧と優先順位
3. 各アクションの詳細
4. 推奨する実施順序・進め方
5. 効果確認の方法
6. 人とLLMで検討する事項

`reports/` にはこの2ファイルだけを保存する。常に最新版へ置き換え、過去版や
実行IDを作らない。`actions.md` にはその時点の改善提案だけを記載する。
内部データは `.analysis/current/` に保存する。

## 10. 実行方式

### 一括実行

1. `prompts/01_ANALYZE.md` を実行して `reports/analysis.md` を作る。
2. 分析を読み直し、事実と仮説が分かれていることを確認する。
3. `prompts/02_PROPOSE_ACTIONS.md` を実行して `reports/actions.md` を作る。
4. 分析と提案の役割が混ざっていないことを確認する。

### 2段階実行

`prompts/RUN_ANALYSIS_STEP_BY_STEP.md` の指示に従い、分析後に一度停止する。

## 11. 禁止事項

- 実測、計算、観察、仮説、提案を混同する
- 一般的なWebマーケティングの成功基準をそのまま適用する
- 売上や急速な規模拡大を目的にする
- コミュニティの緩やかさや自主性を損なう
- データ不足を課題の存在へ読み替える
- 実施済みアクションを言い換えて再提案する
- 数値変化と実施済みアクションの因果を断定する
- 分析実行中にサイト、計測、入力ファイルを変更する
- 秘密情報や不要な個人情報を出力する
- 統計的な精度やデータ量だけを理由に、目的に沿った提案を除外する
- Webサイト改修だけに限定し、関連する現実世界の施策を検討対象外にする
- `actions.md` に現在の改善提案以外の管理欄や過去一覧を作る

## 12. 完了確認

- 取得できたデータと取得できなかったデータを区別した
- LP・ブログ×3対象者の目的を分析した
- 前期比較と、可能な場合は前年同期比較を行った
- 必要な図表に期間、条件、単位を付けた
- 事実と原因仮説を分離した
- `analysis.md` にアクション案を混入させていない
- データ、実査、目的、実務仮説を使って幅広くアクションを検討した
- 各アクション案の起点と対応目的を明示した
- A / B / Cまたは計測・基盤を明示した
- 人が実行可否を判断できる具体性がある
- Webサイト改善と関連する現実世界の施策を検討した
- 統計的有意差や大きなサンプルを提案条件にしていない
- 実施済み内容を重複提案していない
- `actions.md` に現在の改善提案だけを記載した

アクション実行の最終判断は人が行う。
