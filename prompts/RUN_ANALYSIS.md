# HAGAKURE Web分析・改善提案 — マスタープロンプト

このファイルは、HAGAKUREプログラミング塾のWeb分析と改善提案に必要な前提、
判断基準、成果物をまとめた実行指示である。一括実行ではこのファイルを使用し、
2段階実行では同じ要件を分析段階と提案段階に分けて使用する。

## 実行依頼

```text
prompts/RUN_ANALYSIS.mdを読み、Web分析を実行してください。
対象期間: 2026年7月
```

利用者は対象期間だけを自然な文章で指定する。ID、連番、保存先、コマンド引数を
利用者へ求めない。

## あなたの役割

次の実務視点を使い分ける。

- Webアナリスト: GA4・GSC・サイト実査から事実と原因仮説を整理する
- 広報・マーケティングコンサルタント: 外部者への認知、理解、関心、参加導線を検討する
- コンテンツ・編集担当: ブログのテーマ、記事、投稿環境、内部導線を検討する
- コミュニティ運営支援者: 自主性、学び、共有、参加者負担を考慮する
- ITサービス運営支援者: 実装、計測、レビュー、公開、振り返りを検討する

一般論を当てはめるのではなく、取得したデータ、公開サイト、運用記録と、
以下のWebサイト運営目的を判断基準にする。提案は行うが、月次分析の実行中に
実装・公開は行わない。実行の最終判断と公開は人が行う。人が実施内容を明示的に
承認した後は、月次分析とは別の通常依頼としてAIへ実装・検証を依頼できる。

## 6. 第1段階 — データ収集

### GA4

GA4 APIから、利用可能な範囲で次を取得する。

- ユーザー数、新規ユーザー数
- セッション数
- エンゲージメントのあったセッション、エンゲージメント率・時間
- ページビュー、ページ別閲覧
- 流入元・メディア
- デバイス、地域
- コンバージョンまたはキーイベント
- 参加フォームへのリンククリック
- サイト内行動

取得できない項目は、未取得・未計測・API非対応・権限不足など理由を区別する。

### Google Search Console

- 検索クエリ
- 表示回数、クリック数、CTR、平均掲載順位
- ランディングページ
- デバイス、国・地域

### 公開サイト

LPとブログの全要素を機械的に点検するのではなく、Webサイト運営目的とデータ上の
変化から実査するページと導線を選ぶ。少なくとも、目的達成の中心となるページ、
変化への寄与や表示機会が大きいページ、数値の解釈に実査が必要なページを候補にする。
各ページについて、選んだ理由、実査日時、確認方法、確認できなかったことを記録する。

画面上の情報の優先順位、文脈、操作は公開ページのレンダリング結果を根拠にする。
タイトル、メタディスクリプション、見出し階層、リンク先、HTML要素、代替テキストなどは
必要に応じてサイトソース `/Users/itaru/cursor_project/hagakure_blog/` も確認する。
同じ事実を「公開サイト」と「ソース」に分けて重複記載せず、画面で生じる利用者への
影響と、その根拠となる実装を一つの観察として関連付ける。ソースだけを見て、視覚的な
優先順位、モバイルでの使いやすさ、速度、キーボード操作を確認済みとしない。

### 収集条件

- 対象期間は利用者指定。月指定の場合は暦月へ変換する
- 比較期間は直前の同日数を基本とする
- 取得可能なら前年同期も比較する
- LPとブログを可能な限り分ける
- APIページングにより取得可能な全行を取得する
- API失敗、未計測、0件を区別する
- 実行時にAPIから再取得し、過去の生データと混在させない
- ページ別セッション・ユーザーの合計をサイト全体値として扱わない
- 秘密鍵、トークン、個人情報を成果物へ出力しない

取得処理:

```bash
source .venv/bin/activate
python scripts/collect_analysis_data.py --start <開始日> --end <終了日>
```

内部データは `.analysis/current/` に保存する。

### 現行収集データの粒度

分析前に実際のCSV列と `summary.json` を確認する。現行の標準収集では、当期・前期の
サイト全体集計とページ別データ、当期の日別・クエリ別・チャネル別・デバイス別データ、
当期・前期のフォームリンククリックを取得する。日別、クエリ、チャネル、デバイスは
それぞれ独立した集計であり、クエリ×ページ、チャネル×ページ、デバイス×ページ、
フォームクリック元ページの組み合わせではない。ファイルが存在しない、列がない、
比較期間がない場合は、別の集計から組み合わせを復元しない。

## 7. 第1段階 — 可視化と分析

分析中は改善アクションを考えない。提案に都合のよい事実や仮説を作らない。

### 分析方法の選択

最初に、各Webサイト運営目的について「何を判断するために、どのデータと実査が
必要か」という分析質問を置く。取得できたデータの粒度、欠損、期間、件数を確認し、
次の型から質問に答えるために必要なものだけを選ぶ。すべての型を毎回出力することや、
グラフを作ること自体を目的にしない。採用した型とその理由、採用できなかった重要な型と
不足データをレポートから分かるようにする。

| データの状態・分析したいこと | 選ぶ分析の型 | 明らかにすること |
| --- | --- | --- |
| 全体指標が前期から動いた | 期間比較と寄与分解 | 合計差だけでなく、LP / ブログ、ページなど同じ指標を加算できる構成要素の絶対差を出し、全体変化を主に生んだ要素と、反対方向に動いた要素を特定する |
| 日別データに傾向や特定日の変化がある | 時系列分析 | 期間を通じた方向、単発の山谷、変化後も続く段差を区別し、GSCとGA4の動きや運用記録との時間関係から追加確認対象を選ぶ |
| 同じページなど、対応する粒度で複数指標を取得できた | 指標の組み合わせ | 表示機会、クリック、訪問後の利用など、どの段階に機会または不明点があるかを単一指標より具体的にする |
| ページごとの差が大きい、または役割が異なる | ページ状態分析 | 上位・下位順位ではなく、表示機会はあるがクリックされない、流入後の次の導線が弱い、前期から役割が変わったなど、実査すべき状態を特定する |
| 少数ページへの構成比が大きい | 集中度分析 | 特定記事への依存と、その記事が失速したときの全体影響を明らかにする |
| 連続する行動が同じ計測条件で取得できた | 導線・ファネル分析 | 閲覧からLP移動、フォームリンククリックなど、どの段階まで確認でき、どこから先が未計測かを示す |

期間比較では、率の変化だけで重要度を決めず、当期値、前期値、絶対差、構成比を
併記する。寄与は同じ指標・同じ粒度で加算できる要素に限る。全体差が小さいときは
寄与率が不安定になるため、寄与率を強調せず絶対差を使う。新規出現、前期0件、
少数データは通常の増減率と分ける。

時系列では、日別線を掲載して終わらせない。変化の日付、前後の水準、単発か継続か、
表示回数・クリック・セッションの動きの一致と不一致を読む。そのうえで
`.analysis/current/context.md` と `inputs/action-log.md` の出来事を照合する。
時間的な一致は原因の証明ではないため、無関係な可能性と追加確認方法も残す。

指標を組み合わせるときは、定義と粒度が対応していることを先に確認する。例えば、
ページ単位では表示回数・CTR・平均掲載順位と、クリック・セッション・
エンゲージメントを並べて状態を読むことができる。ただし、GSCクリックとGA4セッションは
計測条件が異なり、別々の集計値を個人単位の連続ファネルや転換率として扱わない。
検索クエリ×遷移先ページ、流入チャネル×ページ、デバイス×ページ、フォームクリック元
ページなどの交差データが無ければ、その対応を推測で補わず「未取得」とする。

### 可視化

関係の理解に必要な場合だけ、時系列、棒グラフ、構成比、散布図、ファネル、比較表を使う。
選んだ分析質問への答えが表の方が明確なら、グラフを作らない。すべての図表に、
指標名、対象期間、比較期間、集計条件、単位、データ上の制約を明記する。

### データから実査へ進み、分析へ戻す

データ分析とサイト実査を別々の章の作業で終わらせず、次の往復を行う。

1. 期間比較、時系列、指標の組み合わせから、運営目的に関係する問いを作る。
2. 変化への寄与、表示機会、依存度、導線上の役割を根拠に、実査対象ページを絞る。
3. 選んだページで、コンテンツ、情報設計、ナビゲーション、CTAを確認する。
4. 観察結果を数値の解釈へ戻し、当初の解釈を支持するか、否定するか、
   判断不能のままかを明記する。
5. 事実と観察から原因仮説、代替仮説、追加データを整理する。

例えば、高表示・低CTRならtitle、description、主要クエリから期待される内容と
ページ冒頭の対応を確認する。クリックの多い記事なら、記事がコミュニティの学習事例だと
理解できるか、関連記事やLPへ進めるかを確認する。モバイル利用が無視できない場合は
モバイル表示で主要情報、ナビゲーション、CTAまでの到達と操作を確認する。
フォームリンククリックを読む場合は、クリック前に参加判断の材料と遷移先の説明が
あるかを確認する。交差データが無い場合は、関係を確認したことにせず、ページ選定の
仮説として扱う。

### コンテンツの定性分析

ページを、title、見出し、CTAなど個別要素の有無ではなく、対象者を目的達成へつなぐ
一つの情報体験として読む。まずそのページの対象者、訪問理由、サイト全体での役割、
読後に理解または実行してほしいことを、公開内容と運営目的から定義する。そのうえで、
関係する観点だけを選んで次を分析する。

- 情報の伝わり方: 主題と対象者が冒頭で分かるか、読む理由と必要な前提が示されるか、
  重要な情報が理解しやすい順序にあり、見出しと本文が対応しているか、説明が重複・分散
  して全体像を妨げていないか。
- 利用者の疑問と判断: 訪問理由に答え、次に生じる疑問を先回りできているか。参加、
  閲覧、紹介、投稿などの判断材料、不安を解消する説明、実際の導線が一致しているか。
- ページ間の役割: LPとブログの役割が分かれつつ接続されているか。ブログ記事が
  単独の技術情報で終わらず活動との関係を伝えるか。LPから活動事例、記事から関連情報や
  参加案内、ブログ一覧から目的に合う記事へ移動できるか。
- 検索期待との対応: 取得できた粒度の範囲で、検索クエリとtitle、titleと見出し・本文、
  検索結果から期待される内容とページ内容が対応するか。記事固有のtitle、description、
  OGPがあり、検索流入を得る記事がサイト内の他の役割へ接続されているか。

分析結果は観点を順番に列挙せず、「役割を果たしている点」「役割を妨げている点」
「改善余地がある点」にまとめる。各判断には、対象URL、画面上の位置、実際の見出し・
リンク文言などの観察根拠を付ける。利用者が理解した、迷ったという心理は、行動データや
利用者調査が無ければ事実として書かない。

### UI・情報設計・導線の分析

見た目の好みではなく、「現在地と内容を理解し、必要な情報を得て、次の行動を選べるか」
というタスクで評価する。データとページの役割から関係する観点を選び、次の流れを
デスクトップとモバイルで必要に応じて確認する。

- 情報設計: 最初の画面と見出し構造から内容・目的・優先順位が分かるか。重要情報が
  判断する箇所より前にあり、関係する情報がまとまり、長いページでも全体構造を追えるか。
- ナビゲーション: LP、ブログ、活動事例、参加案内の関係と現在地が分かるか。
  一覧カードから記事内容を判断でき、記事を読んだ後に関連情報やLPへ進めるか。
- CTA: 実際の文言、位置、リンク先、同目的CTAの一貫性を確認する。押した後に起きること、
  外部フォームへ移動することを予測でき、CTAより前に判断材料があり、ページ内容から
  行動へ自然につながるか。主要CTAと競合するリンクがないか。
- モバイル: 情報の順序、主要情報・CTAまでの距離、ナビゲーション、文章・表の可読性、
  タップ対象を確認し、PC版を縮小しただけで利用上の順序が崩れていないかを見る。
- アクセシビリティと一貫性: 見出し階層、リンクとボタンの役割、画像の代替情報、
  同種要素の表現、色だけに依存しない意味、キーボード操作とフォーカス状態を確認する。

実ブラウザまたは実機相当の表示で確認していない事項は「未確認」とする。レスポンシブ用
meta要素やCSSがあることだけで、モバイル表示や操作性を「問題なし」と判定しない。

### 目的別分析

6つのWebサイト運営目的について、次を整理する。

| サイト・対象者 | 運営目的 | 確認できた事実 | 判定 | 判断できないこと |
| --- | --- | --- | --- | --- |

判定は次のいずれかに限定する。

- 確認できた
- 課題または改善機会を確認できた
- データ不足で判断できない

データ不足を課題の存在へ読み替えない。別の対象者の指標で代用しない。

### LPの分析観点

- 外部者にコミュニティの趣旨や活動内容が伝わっているか
- 参加検討に必要な情報があるか
- 検索・外部サイトから訪問を獲得できているか
- 訪問者が参加申し込みや関連ページへ移動しているか
- 参加者が紹介用ツールとして利用しやすいか
- 開発・運営を技術習得・サービス運営経験として確認できるか

### ブログの分析観点

- 外部者が活動事例・学習事例を知る入口になっているか
- 検索流入を獲得できているか
- どのテーマ・記事が読まれているか
- 記事からLPや参加案内への移動があるか
- 参加者のアウトプットの場所・機会として利用されているか
- 投稿者数、記事数、更新頻度がどう変化しているか
- 投稿を始めやすく、編集・共有・反応につながる環境か
- 投稿・編集・改善・計測を運営経験として確認できるか

### 原因仮説

| 確認された事実 | 原因の仮説 | 仮説の根拠 | 確度 | 代替仮説 | 追加データ | 検証方法 |
| --- | --- | --- | --- | --- | --- | --- |

事実、計算、観察、運用記録、仮説を区別する。時期が一致するだけで、
外部イベントや実施済みアクションの効果を断定しない。

## 8. 第2段階 — 改善アクションの検討

`reports/analysis.md` を主要入力とする。人が修正している場合は修正後を正とする。
データと分析結果を重要な参考情報として使うが、それだけを提案可否の条件にしない。

### アクション検討でのデータの位置づけ

- 統計的有意差や大きなサンプル数を、提案の必須条件にしない。
- データが少ない、期間が短い、一部が未計測という理由だけで提案を止めない。
- データから直接導ける案に加え、サイト実査、運営目的、外部イベント、実施記録、
  広報・編集・コミュニティ運営・ITサービス運営の知見からも提案する。
- 定量データで判断できない領域では、定性確認や実務仮説を使ってよい。
- データで確認した事実と、目的・観察・実務知見から考えた内容は明確に区別する。
- 数値効果を保証せず、実行後の定量・定性情報を次回改善へ活用する。

### 提案の起点

各アクション案に、主な起点を一つ以上記載する。

- データ起点: GA4・GSC・記事数・投稿者数などを参考にした案
- サイト実査起点: コンテンツ、導線、CTA、投稿環境などの観察から考えた案
- 目的起点: 6つのWebサイト運営目的を前進させるための案
- 実務仮説起点: 広報、マーケティング、編集、コミュニティ運営、
  ITサービス運営の知見から考えた案

直接データで裏付けられない案も、目的との関係、提案理由、想定する効果、
確認方法を説明できれば提案してよい。

### 提案対象

- タイトル、見出し、本文、CTA、内部リンク
- LP・ブログの導線、情報構造、デザイン
- 既存記事の更新、記事テーマ・カテゴリー整理
- 新しいコンテンツ企画
- 検索・外部流入・広報に対応する具体的なコンテンツと受け皿
- CMS、投稿画面、テンプレート、編集支援
- 参加者が投稿・編集・運営へ関わりやすくするWeb上の仕組み
- 計測、レビュー、公開、保守、振り返りの運用改善
- SNS、メール、外部メディア、地域団体との連携などの広報
- 参加者へのインタビュー、投稿支援、勉強会、イベント、記事づくり
- サイト開発や運営を学習機会にする改善プロジェクト

現実世界の施策も積極的に検討してよい。Webサイトまたはコミュニティのどの目的に
寄与するか、誰にどのような変化を期待するか、Webサイトとどう連動するかを具体化する。

### A / B / C分類

- A: すぐに実行でき、短期的な反応が期待できる
- B: すぐに実行でき、長期的な反応が期待できる
- C: 実行に時間がかかるが、長期的な反応が期待できる
- 計測・基盤: 継続改善やKGI確認のために必要な計測・運営基盤

短期・中長期、Web改修・コンテンツ・広報・コミュニティ運営など、異なる方向性を
目的に応じて検討する。施策の規模や期間を一律に制限しない。

### 各アクション案の必須項目

| 項目 | 内容 |
| --- | --- |
| アクション名 | 実行する施策の名称 |
| 分類 | A / B / Cまたは計測・基盤 |
| 提案の起点 | データ、サイト実査、目的、実務仮説のいずれか |
| 対象サイト | LP、ブログ、または両方 |
| 対象者 | 外部者、参加者、開発・運営者 |
| 対応する運営目的 | 上記目的表の文言 |
| 現状認識 | データ、サイト観察、運用状況、目的から見た機会 |
| 提案理由 | なぜ目的達成に寄与すると考えるか |
| 実施内容 | Web改修、制作物、文案、配信、イベント、運用変更など |
| 期待する効果 | 対象者の状態と指標がどう変わる想定か |
| 優先度 | 高・中・低と理由 |
| 効果確認 | 定量・定性の確認項目、確認時期 |
| 実行条件 | 担当役割、概算人時、必要スキル、費用、依存関係 |
| 留意点 | 参加者負担、運営負担、誤解、継続性など |
| 完了条件 | 何が揃えば実施完了か |

手動で管理するIDや連番は使用しない。

### 優先順位

- Webサイト運営目的との整合性
- コミュニティ全体の目的との整合性
- 期待できる価値と効果が現れるまでの期間
- 実行負担、継続負担、費用、リスク
- 学ぶ楽しさ、気軽な参加・共有、教え合い
- 地域の人同士が緩やかにつながれること
- 参加者へ過度な負担をかけないこと
- サイトの開発・運営自体が学習機会になること
- 実現可能性と実施順序
- データやサイト実査から見た必要性

アクセス増、統計的精度、データ根拠の強さだけで優先順位を決めない。

### 実務的な具体性

「SEO強化」「SNS発信」「CTA改善」「UI改善」「内部リンク追加」
「モバイル対応」「記事を増やす」を、単独のアクション名や実施内容にしない。
Webサイト上の提案では、対象URLまたは機能、変更する見出し・本文・リンク・ボタン・
ナビゲーションと画面上の位置、現在の状態、変更後の内容を特定する。理解を助ける場合は
文言、情報順序、リンク配置などの例を示す。サイト外・運用上の提案でも、対象者、
制作物、配信先、頻度、担当手順を特定する。

根拠は、使用データの指標・期間・値と、実査したURL・観察内容を対応付ける。
データで直接裏付けられない案は、目的起点または実務仮説起点であることと、実行前に
確認する条件を明記する。期待する効果は「CTRを上げる」のような指標だけでなく、
誰が何を理解し、どの行動を選びやすくなるかを書き、その後に既存指標で確認できる変化、
基準値、確認時期を示す。取得できない効果指標を取得済みとして扱わない。

すぐにできる改善だけでなく、継続施策や中長期施策も提案する。推奨する実施順序を
示し、人とLLMが実行内容を検討できるようにする。

## 9. 成果物

### `reports/analysis.md`

1. この期間に分かったこと
2. 使用したデータ・対象期間・比較期間・制約
3. 目的別の達成状況
4. LPの分析結果
5. ブログの分析結果
6. 可視化したグラフ・表
7. 確認された事実と原因仮説
8. 判断できなかったこと・追加データ
9. KGI・KPIの確認と提案

冒頭に「分析結果であり、アクション案ではない」と明記する。

### `reports/actions.md`

1. 今回の改善方針
2. A / B / C分類のアクション一覧と優先順位
3. 各アクションの詳細
4. 推奨する実施順序・進め方
5. 効果確認の方法
6. 人とLLMで検討する事項

このワークフローが `reports/` へ生成・更新する利用者向け成果物はこの2ファイルだけとする。
常に最新版へ置き換え、過去版や実行IDを新たに作らない。既存の旧成果物は分析入力として
使用しない。`actions.md` にはその時点の改善提案だけを記載する。内部データは
`.analysis/current/` に保存する。

## 10. 実行方式

### 一括実行

1. `prompts/01_ANALYZE.md` を実行して `reports/analysis.md` を作る。
2. 分析を読み直し、事実と仮説が分かれていることを確認する。
3. `prompts/02_PROPOSE_ACTIONS.md` を実行して `reports/actions.md` を作る。
4. 分析と提案の役割が混ざっていないことを確認する。

### 2段階実行

`prompts/RUN_ANALYSIS_STEP_BY_STEP.md` の指示に従い、分析後に一度停止する。

## 11. 禁止事項

- 実測、計算、観察、仮説、提案を混同する
- 一般的なWebマーケティングの成功基準をそのまま適用する
- 売上や急速な規模拡大を目的にする
- コミュニティの緩やかさや自主性を損なう
- データ不足を課題の存在へ読み替える
- 実施済みアクションを言い換えて再提案する
- 数値変化と実施済みアクションの因果を断定する
- 分析実行中にサイト、計測、入力ファイルを変更する
- 秘密情報や不要な個人情報を出力する
- 統計的な精度やデータ量だけを理由に、目的に沿った提案を除外する
- Webサイト改修だけに限定し、関連する現実世界の施策を検討対象外にする
- `actions.md` に現在の改善提案以外の管理欄や過去一覧を作る

## 12. 完了確認

- 取得できたデータと取得できなかったデータを区別した
- LP・ブログ×3対象者の目的を分析した
- 分析質問に応じて手法を選び、選んだ理由を説明した
- 全体の増減を、同じ指標・粒度の構成要素へ必要に応じて分解した
- 日別データが解釈に有効な場合、単発と継続の動きを区別した
- 複数指標は対応する粒度だけで組み合わせ、未取得の交差関係を推測で補っていない
- データから実査対象を選び、実査結果を数値の解釈へ戻した
- 実査はページの役割を果たす点、妨げる点、改善余地としてまとめた
- モバイルや操作性を、未確認のまま確認済みとしていない
- 前期比較と、可能な場合は前年同期比較を行った
- 必要な図表に期間、条件、単位を付けた
- 事実と原因仮説を分離した
- `analysis.md` にアクション案を混入させていない
- データ、実査、目的、実務仮説を使って幅広くアクションを検討した
- 各アクション案の起点と対応目的を明示した
- A / B / Cまたは計測・基盤を明示した
- 対象URL・機能、変更箇所、現状、変更内容、根拠、期待する利用者変化、効果指標が
  人の実行判断に必要な粒度で対応している
- Webサイト改善と関連する現実世界の施策を検討した
- 統計的有意差や大きなサンプルを提案条件にしていない
- 実施済み内容を重複提案していない
- `actions.md` に現在の改善提案だけを記載した
